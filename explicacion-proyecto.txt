========================================================
1. RESUMEN DEL PROYECTO
========================================================

Es un sistema de gestión gastronómico full-stack para un restaurante.
Permite administrar empleados, productos, platos con recetas, mesas,
pedidos, caja, reservas y producción.

  - Backend: Django 6.0 + MySQL — API REST hecha a mano (sin DRF)
  - Frontend: React 19 + React Router 7 — SPA con TailwindCSS
  - Autenticación por token custom (no JWT, no sesión)
  - 19 modelos, 39 endpoints, 13 páginas frontend


========================================================
2. STACK TECNOLÓGICO
========================================================

Backend:
  - Python 3.x + Django 6.0.3
  - MySQL (motor de base de datos)
  - django-cors-headers (CORS)
  - No usa Django REST Framework

Frontend:
  - React 19
  - React Router 7
  - react-scripts 5 (Create React App)
  - TailwindCSS
  - jsPDF + jspdf-autotable (generación de PDF en cliente)
  - react-icons
  - No usa axios (fetch nativo)

Infraestructura:
  - .env con credenciales SMTP de Gmail
  - Proxy de desarrollo en package.json
  - Deploy planeado: Vercel (frontend) + Railway/Render (backend)

4.3 PATRÓN DE VISTAS

Todas son function-based views en api/views.py (~2000 líneas).
El patrón típico:

    @csrf_exempt
    def productos_list(request):
        if request.method == 'GET':
            productos = Producto.objects.select_related('categoria').all()
            data = [producto_to_dict(p) for p in productos]
            return JsonResponse(data, safe=False)

        elif request.method == 'POST':
            try:
                data = json.loads(request.body)
            except json.JSONDecodeError:
                return JsonResponse({'error': 'JSON inválido'}, status=400)
            # validación manual campo por campo
            producto = Producto.objects.create(**data)
            return JsonResponse(producto_to_dict(producto), status=201)

        return HttpResponseNotAllowed(['GET', 'POST'])

Características:
  - @csrf_exempt en todas (SPA con token, no cookies)
  - @token_required solo en endpoints sensibles
  - Sin serializers — funciones to_dict() manuales
  - Validación manual con if/else
  - Respuestas con JsonResponse


4.4 DECORADOR TOKEN_REQUIRED

    def token_required(view_func):
        def wrapper(request, *args, **kwargs):
            auth_header = request.headers.get('Authorization', '')
            parts = auth_header.split()
            if len(parts) != 2 or parts[0].lower() != 'token':
                return JsonResponse({'error': 'Token requerido'}, status=401)
            try:
                token = AuthToken.objects.select_related('user').get(key=parts[1])
            except AuthToken.DoesNotExist:
                return JsonResponse({'error': 'Token inválido'}, status=401)
            if not token.user.is_active:
                return JsonResponse({'error': 'Usuario inactivo'}, status=401)
            request.user = token.user
            request.auth_token = token
            return view_func(request, *args, **kwargs)
        return wrapper

  - Busca el header "Authorization: Token <key>"
  - Consulta AuthToken con select_related('user') (optimización)
  - Rechaza con 401 si no existe, formato inválido, o usuario inactivo
  - Setea request.user para usarlo en la vista


4.5 SERIALIZACIÓN MANUAL

No hay serializers de DRF. Cada modelo tiene una función to_dict():

    def producto_to_dict(p):
        return {
            'id': p.id,
            'nombre': p.nombre,
            'categoria': {'id': p.categoria.id, 'nombre': p.categoria.nombre} if p.categoria else None,
            'stock': float(p.stock),
            'precio_compra': float(p.precio_compra) if p.precio_compra else None,
            'unidad': p.unidad,
            'stock_minimo': float(p.stock_minimo),
            'activo': p.activo,
            'fecha_creacion': p.fecha_creacion.isoformat(),
        }


4.6 LÓGICA DE NEGOCIO CLAVE

  a) Auto-desactivación por stock:

     Cuando se modifica stock (vía PATCH producto o al confirmar pedido):
       1. Si stock <= 0 → producto.activo = False
       2. Se llama a desactivar_platos_por_producto(producto)
       3. Esto busca todos los platos cuya receta incluya ese producto
       4. Y los desactiva también (activo = False)

  b) Validación al reactivar plato:

     Si querés reactivar un plato (PATCH con activo=True):
       - Verifica que todos los productos de su receta estén activos
       - Si hay alguno inactivo → error: "No hay productos disponibles"

  c) Confirmar pedido (consume stock):

     POST /api/pedidos/<id>/confirmar/
       1. Cambia estado a "en_preparacion"
       2. Por cada DetallePedido:
            Por cada Receta del plato:
              producto.stock -= (cantidad_receta * cantidad_detalle)
              Si stock <= 0 → desactivar producto + platos asociados

  d) Caja:

     - Solo una caja activa a la vez
     - Al crear caja, si hay otras activas, se cierran automáticamente
     - Pagos generan MovimientoCaja (ingreso) automáticamente
     - Se puede cerrar caja manualmente con monto_final

5.2 AUTH CONTEXT (contexts/AuthContext.js)

  Provee a toda la app: { user, empleado, token, loading, login, logout, saveSession }

  login(username, password):
    1. POST /api/auth/login/ con username + password
    2. Guarda auth_token en localStorage
    3. Guarda auth_data (JSON con user + empleado) en localStorage
    4. Actualiza estado global

  logout():
    1. POST /api/auth/logout/ con Authorization: Token <key>
    2. Limpia localStorage (auth_token, auth_data)
    3. Resetea estado global

  Al montar el componente:
    1. Lee token de localStorage
    2. Si existe, hace GET /api/auth/me/
    3. Si ok → guarda user + empleado en estado
    4. Si falla (token expirado/inválido) → limpia sesión


5.3 COMUNICACIÓN CON EL API

  No hay una capa de servicios compartida. Cada página define su helper:

  --- Sin token (AdminProductos, AdminEmpleados, AdminPlatos) ---
    const api = (url, opts) =>
      fetch(url, { headers: { 'Content-Type': 'application/json' }, ...opts })
        .then(r => r.ok ? r.json() : r.json().then(d => { throw new Error(d.error); }));

  --- Con token (AdminPedidos, AdminCaja, AdminReservas) ---
    function api(url, opts = {}) {
      const token = localStorage.getItem('auth_token');
      return fetch(url, {
        headers: {
          'Content-Type': 'application/json',
          ...(token ? { Authorization: `Token ${token}` } : {}),
        },
        ...opts,
      }).then(r => r.ok ? r.json() : r.json().then(d => { throw new Error(d.error); }));
    }

  --- Image upload ---
    const fd = new FormData();
    fd.append('imagen', file);
    const token = localStorage.getItem('auth_token');
    fetch('/api/upload-imagen/', {
      method: 'POST',
      headers: token ? { Authorization: `Token ${token}` } : {},
      body: fd,
    });

7. AUTENTICACIÓN Y ROLES
========================================================

  Modelo de autenticación:

    User (Django auth)
      │
      ├── AuthToken (token custom de 64 chars hex)
      │
      └── Empleado (OneToOne)
              │
              └── Rol (FK)
                    │
                    └── Group (OneToOne, sincronizado automáticamente)

  Flujo:
    1. POST /api/auth/login/ → Django crea AuthToken, devuelve { token, user, empleado }
    2. Frontend guarda token en localStorage
    3. Cada request protegido envía: Authorization: Token <key>
    4. GET /api/auth/me/ verifica token al cargar la app
    5. POST /api/auth/logout/ elimina token de la BD

  Roles:
    - El modelo Rol existe y permite crear cualquier rol
    - No hay roles predefinidos (no hay seed data)
    - Está vinculado a Group de Django pero sin asignar permisos
    - La autorización se hace inline: rol__nombre='Mesero'
    - No se usa has_perm() ni permission_required

8. FLUJOS IMPORTANTES
========================================================

8.1 CREAR Y CONFIRMAR UN PEDIDO

  1. AdminPedidos carga datos iniciales:
       GET /api/mesas/              → para elegir mesa
       GET /api/empleados/?rol=Mesero → para asignar mesero
       GET /api/platos/             → para el carrito
       GET /api/productos/          → para ver disponibilidad

  2. POST /api/pedidos/ (requiere auth)
       Body: { mesa_id, empleado_id, total, detalles: [{plato_id, cantidad, precio_unitario, subtotal}] }
       → Crea Pedido + DetallePedido
       → Valida que haya una caja activa
       → Estado inicial: "abierto"

  3. POST /api/pedidos/<id>/confirmar/ (requiere auth)
       → Consume stock:
           Por cada DetallePedido:
             Por cada Receta del plato:
               producto.stock -= (cantidad_receta * cantidad_detalle)
               Si stock <= 0 → producto.activo = False
               → desactivar_platos_por_producto(producto)
       → Cambia estado a "en_preparacion"

  4. PATCH /api/pedidos/<id>/ (requiere auth)
       → Cambia estado: servido → cerrado

  5. POST /api/pagos/ (requiere auth)
       Body: { pedido_id, monto, metodo, vuelto }
       → Crea Pago
       → Crea Ticket
       → Crea MovimientoCaja (tipo='ingreso') en caja activa
       → Pedido.estado → "pagado"

8.2 AUTO-DESACTIVACIÓN DE STOCK

  Disparadores:
    - PATCH /api/productos/<id>/ (si se modifica stock manualmente)
    - POST /api/pedidos/<id>/confirmar/ (consume stock)
    - POST /api/ordenar/ (endpoint público, consume stock directo)

  Efecto en cascada:
    1. Producto.stock se modifica
    2. Si stock <= 0 → producto.activo = False
    3. Se ejecuta desactivar_platos_por_producto(producto)
    4. Busca todos los platos cuya receta incluya ese producto
    5. plato.activo = False
    6. Si después se intenta reactivar el plato:
       Valida que todos los productos de su receta estén activos
       Si hay inactivos → error 400

8.3 CAJA REGISTRADORA

  Apertura:
    POST /api/cajas/
      Body: { empleado_apertura_id, monto_inicial }
      → Si hay otra caja activa, la cierra automáticamente
      → Crea nueva caja con activa=True

  Movimientos:
    - Ingresos: se generan automáticamente al registrar un pago
    - Egresos: POST /api/movimientos-caja/ manuales
    - GET /api/movimientos-caja/?caja_id= para listar

  Cierre:
    PATCH /api/cajas/<id>/
      Body: { cerrar: true, empleado_cierre_id, monto_final }
      → activa = False
      → fecha_cierre = ahora
      → Guarda monto_final

  Auth en productos/platos.. | ❌ Sin protección
  CSRF                       | ❌ @csrf_exempt en todas
  Token storage              | localStorage (vulnerable a XSS)
  CORS                       | CORS_ALLOW_ALL_ORIGINS = True
  DEBUG                      | True
  SECRET_KEY                 | Hardcodeada en settings.py
  ALLOWED_HOSTS              | [] (vacío)
  Contraseñas                | ✅ Hasheadas con PBKDF2
  Rate limiting              | ❌ No implementado
  HTTPS                      | ❌ No configurado
  Expiración de tokens       | ❌ Tokens indefinidos
  Credenciales en git        | ❌ .env con credenciales Gmail commiteadas

  Resumen: el backend está abierto. Cualquiera con acceso a la red
  puede crear/modificar/eliminar productos, platos, empleados, roles,
  mesas, etc. Solo pedidos, pagos, caja, reservas requieren token.

11. PREGUNTAS Y RESPUESTAS PARA ENTREVISTA
========================================================

P: ¿Por qué no usaste Django REST Framework?
R: Lo consideré, pero para este proyecto preferí mantenerlo simple.
   Las vistas son function-based con JsonResponse y funciones to_dict()
   manuales. DRF agrega serializers, viewsets, routers — mucha abstracción
   que para un proyecto de este tamaño no justificaba. Si escala, migrar
   a DRF sería lo primero.

P: ¿Por qué token auth y no JWT o sesiones?
R: Las sesiones de Django no funcionan bien con SPA porque usan cookies y
   requieren CSRF. JWT es excelente pero requiere refresh tokens, expiración,
   y más librerías. Nuestro token es simple: se crea en login, se envía como
   Authorization: Token <key>, se borra en logout. Para un sistema interno
   de restaurante es suficiente.

P: ¿Cómo manejás la autenticación en el frontend?
R: Con un AuthContext que envuelve la app. Tiene login() que guarda token
   en localStorage, logout() que lo elimina, y al cargar verifica el token
   con /api/auth/me/. Las rutas admin están protegidas con AdminRoute.

P: ¿Cómo evitás CORS en desarrollo?
R: Con un proxy en package.json: "proxy": "http://127.0.0.1:8000". El
   navegador pide a localhost:3000 y React Dev Server reenvía a Django.

P: ¿Por qué no usás axios?
R: fetch() es nativo y suficiente para GET/POST/PATCH/DELETE con JSON.
   Cada página define un helper api() que normaliza errores. Si necesito
   interceptors o timeouts en el futuro, pasaría a axios.

P: ¿Cómo funciona el sistema de roles?
R: El modelo Rol está vinculado a Group de Django mediante OneToOneField.
   Al guardar un Rol, se sincroniza automáticamente el Group. Pero no
   usamos los permisos de Django. La autorización es inline con filtros
   como rol__nombre='Mesero'. Tenemos pendiente migrar a permisos custom.

P: ¿Cómo manejás el stock?
R: Al confirmar un pedido, recorremos los DetallePedido, por cada plato
   obtenemos su Receta (qué productos y cantidades necesita), y restamos
   del stock. Si stock <= 0, se desactiva el producto y también los platos
   que lo usan (en cascada).

P: ¿Qué pasa si reactivás un plato con productos inactivos?
R: El endpoint valida que todos los productos de la receta estén activos.
   Si hay inactivos, responde con error 400.

P: ¿Usás los permisos de Django?
R: Todavía no. El modelo Rol tiene el OneToOne a Group, y los Groups se
   sincronizan automáticamente, pero nunca asignamos permisos. La idea
   es migrar a Django Model Permissions con permisos custom como
   'ajustar_stock', 'cerrar_caja', etc.

P: ¿Cuáles son los mayores problemas de seguridad del proyecto?
R: 1) La mayoría de endpoints no requieren autenticación (productos,
   platos, empleados, roles). 2) CORS abierto a todos los orígenes.
   3) DEBUG=True en producción. 4) Secret Key hardcodeada. 5) Tokens
   en localStorage sin expiración. 6) Credenciales de email commiteadas.

P: ¿Cómo harías deploy?
R: Frontend en Vercel, backend en Railway/Render. Configurar ALLOWED_HOSTS,
   DEBUG=False, SECRET_KEY como variable de entorno, restringir CORS,
   y migrar la base de datos MySQL a un servicio cloud.

P: Si tuvieras que migrar a DRF, ¿por dónde empezarías?
R: Por los serializers (reemplazar to_dict() con ModelSerializer), después
   ViewSets con routers, después autenticación con DRF TokenAuthentication,
   después documentación con drf-spectacular. Módulo por módulo.

P: ¿Cómo modelaste la relación User-Empleado-Rol?
R: User (Django auth) tiene OneToOne con Empleado, que agrega datos
   laborales. Empleado tiene FK a Rol. Rol tiene OneToOne con Group.
   Cada rol puede tener múltiples empleados, cada empleado tiene un rol.

P: ¿Cómo implementaste el módulo de caja?
R: Con el modelo Caja (fecha_apertura, fecha_cierre, monto_inicial,
   monto_final, activa). Solo una caja activa a la vez. Pagos generan
   MovimientoCaja automáticamente. Se puede cerrar manualmente.

P: ¿Cómo funciona el módulo de producción?
R: RecetaProducto define qué insumos necesita un producto compuesto y en
   qué cantidades. Produccion registra un lote de elaboración: consume
   los insumos (resta stock) y produce el producto final (suma stock).

P: ¿Qué harías si mañana tenés que dar soporte a 50 restaurantes?
R: Agregaría un modelo Restaurant con subdominio, pondría FK restaurant_id
   en todos los modelos, y un middleware que filtre automáticamente por
   subdominio. Es multi-tenant con DB compartida, no separada.


--- Más preguntas de entrevista ---


P: ¿Por qué usás MySQL y no PostgreSQL?
R: El proyecto arrancó con MySQL porque era la base que ya tenía disponible
   en el entorno. Para un restaurante, cualquiera de los dos funciona bien.
   PostgreSQL tiene mejor soporte para operaciones concurrentes y tipos de
   datos como JSONB, pero acá no los necesitamos. Si el proyecto escalara,
   PostgreSQL sería mi elección.

P: ¿Cómo manejás las migraciones cuando trabajan varios desarrolladores?
R: Django gestiona las migraciones automáticamente con makemigrations y
   migrate. Cada desarrollador ejecuta makemigrations cuando cambia modelos
   y commitea el archivo generado. El resto del equipo aplica migrate al
   bajar los cambios. Si hay conflictos, se resuelven como cualquier conflicto
   de git. Nunca editamos migraciones existentes, siempre creamos nuevas.

P: ¿Cómo optimizarías una consulta que trae todos los pedidos con sus detalles?
R: Usaría select_related para las FK directas (mesa, empleado) y
   prefetch_related para las relaciones inversas (detallepedido_set).
   Algo como: Pedido.objects.select_related('mesa','empleado')
   .prefetch_related(
       Prefetch('detallepedido_set',
           queryset=DetallePedido.objects.select_related('plato'))
   ).all(). También agregaría índices compuestos en (estado, fecha_creacion)
   para filtrar rápido.

P: ¿Qué pasa si dos usuarios confirman un pedido al mismo tiempo?
R: Es una race condition. Se soluciona con transaction.atomic() y
   select_for_update() para bloquear las filas de stock mientras se
   procesa la confirmación. Así, el segundo usuario espera a que el
   primero termine y ve el stock actualizado. Hoy no lo tenemos
   implementado y podría haber problemas de concurrencia.

P: ¿Por qué algunas vistas devuelven safe=False en JsonResponse?
R: safe=False permite devolver listas en vez de diccionarios.
   JsonResponse por defecto solo acepta dicts. Cuando devolvemos
   una lista de productos o platos, necesitamos safe=False.
   Ejemplo: JsonResponse([producto_to_dict(p) for p in productos], safe=False).

P: ¿Cómo validás los datos si no tenés serializers? ¿No es propenso a errores?
R: Sí, es propenso a errores. Hoy validamos manualmente con if/else después
   de json.loads(). Es frágil y repetitivo. Es uno de los motivos por los
   que migrar a DRF estaría en el backlog — los serializers dan validación
   automática, mensajes de error consistentes y menos código.

P: ¿Cómo manejás los errores de base de datos?
R: Con try/except básico. Por ejemplo, IntegrityError si se viola una
   constraint unique, o DoesNotExist si no se encuentra un objeto.
   Django ya protege contra SQL injection porque usa ORM con queries
   parametrizadas. Para errores más graves, Django retorna 500 al cliente.

P: ¿Por qué usás select_related en algunas consultas y no en otras?
R: select_related hace JOIN en la misma consulta SQL. Lo uso cuando sé
   que voy a acceder a la FK de cada objeto (ej: Producto.categoria).
   Lo omito en consultas donde solo necesito los datos del modelo base
   o donde ya hay prefetch_related para relaciones inversas.

P: ¿Cuánto tardaría en responder /api/productos/ con 10.000 productos?
R: Depende de cuántos JOIN haga y si hay índices. Con select_related a
   categoria y 10.000 filas, estimo entre 200ms y 500ms en MySQL local.
   El cuello de botella sería la serialización (recorrer 10.000 productos
   llamando a producto_to_dict()). Para mejorar, agregaría paginación
   server-side (limit/offset) y filtros por query params.

P: ¿Por qué usás Create React App y no Vite?
R: El proyecto arrancó hace meses y CRA era el estándar. Hoy Vite es
   más rápido (HMR instantáneo, build más rápido) y sería mi elección
   si empezara de nuevo. Migrar a Vite implica reconfigurar el proxy,
   el testing y los builds, y no justifica el esfuerzo ahora.

P: ¿Cómo manejarías el estado global si la app creciera?
R: Hoy usamos Context solo para auth. Si creciera, evaluaría Zustand
   (liviano, simple) o Redux Toolkit (más estructura, middlewares).
   Context es suficiente para estado global chico, pero causa re-renders
   innecesarios si se usa para muchos datos que cambian frecuentemente.

P: ¿Por qué el Dashboard tiene datos mockeados y no llama a la API?
R: Es una deuda técnica. Lo dejé mockeado para tener algo visual mientras
   desarrollaba otras funcionalidades. Lo pendiente es crear endpoints
   de estadísticas (ventas del día, platos más vendidos, ocupación, etc.)
   y conectar el dashboard a esos datos reales.

P: ¿Cómo evitarías que el sidebar del admin se recargue en cada navegación?
R: Ya no debería recargarse. Al usar React Router con rutas anidadas
   dentro de AdminLayout, el sidebar se monta una vez y solo cambia el
   contenido del <Outlet/> al navegar. Si recargara, sería porque cada
   página admin tiene su propia llamada a datos en useEffect, no porque
   se remonte el layout.

P: ¿Cómo implementarías los filtros del lado del servidor en vez del cliente?
R: Agregaría query params en los endpoints: /api/productos/?categoria=X
   &activo=true&search=algo. En la vista, filtraría el queryset con
   filter() antes de serializar. El frontend enviaría los filtros como
   parámetros en la URL. Esto es más eficiente para conjuntos grandes
   porque la BD hace el trabajo pesado.

P: ¿Por qué algunos componentes repiten el helper api() en vez de tener
   uno compartido?
R: Deuda técnica. Arrancamos copiando el patrón de un componente a otro
   sin refactorizar. Lo ideal sería tener un archivo api.js con una
   función genérica que todos importen. Es un refactor simple que planeamos
   hacer.

P: ¿Cómo manejás el loading state en las páginas?
R: Con un estado local loading (useState que arranca en true y pasa a
   false cuando llega la respuesta). Mientras carga, mostramos un mensaje
   o spinner condicional. También manejamos error con otro estado. No
   tenemos un sistema de loading global ni suspense.

P: ¿Cómo modelaste el inventario? ¿Por qué no usás un histórico de
   movimientos de stock?
R: Hoy el stock es un campo que se actualiza directamente (suma/resta).
   No hay un log de movimientos. Esto es una limitación: no podemos
   auditar quién y cuándo modificó el stock. Una mejora sería crear un
   modelo MovimientoStock con tipo (ingreso/egreso), cantidad, referencia
   (pedido/producción/ajuste), usuario y timestamp. Y el stock se
   calcularía como suma de movimientos o se mantendría como campo
   denormalizado para performance.

P: ¿Qué índice le pondrías a la tabla Pedido para filtrar por fecha y estado?
R: Un índice compuesto: (estado, fecha_creacion). Así las consultas
   del tipo "pedidos activos de hoy" usan el índice completo. También
   uno simple en (mesa_id) para buscar pedidos de una mesa.

P: ¿Por qué Receta tiene unique_together?
R: Para evitar que un mismo producto se agregue dos veces a la receta
   del mismo plato. No tiene sentido que un plato requiera "harina" dos
   veces con cantidades separadas. Si necesita más cantidad, se actualiza
   la existente.

P: Si un cliente pide 5 platos, ¿cuántas tablas se actualizan?
R: 1 Pedido, 5 DetallePedido, N productos (según recetas), y si algún
   producto llega a stock 0, se actualiza producto.activo y plato.activo.
   Además, si se paga: 1 Pago, 1 Ticket, 1 MovimientoCaja. En total
   entre 8 y 15 tablas afectadas.

P: ¿Cuánto tiempo te tomó desarrollar esto? ¿Qué fue lo más complejo?

   CRUDs repetitivos.

P: Si pudieras reescribir algo desde cero, ¿qué cambiarías?
R: Usaría DRF desde el principio para tener serializers, validación y

P: ¿Cómo harías para que el menú público funcione sin JavaScript?

P: ¿Cómo integrarías un sistema de delivery tipo Rappi con esta API?

P: ¿Qué endpoints creés que son los más lentos y cómo los mejorarías?

P: ¿Probaste la API? ¿Cómo?

--- Manejo de errores ---

P: ¿Cómo manejás los errores en el backend?
R: Con try/except alrededor de json.loads() y las operaciones de BD.
   Cada vista devuelve JsonResponse con el error y un status code
   apropiado (400, 401, 404, 500). No hay un middleware global de
   manejo de excepciones. Mejoraría creando un decorador o middleware
   que capture excepciones no manejadas y devuelva un JSON consistente.

P: ¿Qué pasa si el servidor de MySQL se cae?

   error 500. No hay manejo especial. En producción agregaría: 1) Retry
   con backoff para reconexión. 2) Timeout configurable en la BD.
   3) Health check endpoint que verifique BD. 4) Logging de errores
   con alerta.

--- Seguridad avanzada ---

P: ¿Cómo prevenirías SQL injection?
R: Django ORM ya lo hace automáticamente usando queries parametrizadas.
   Mientras no uses raw() o extra() con strings concatenados, estás
   protegido. En este proyecto no usamos raw queries, así que no hay
   riesgo de SQL injection.

P: ¿Cómo prevenirías XSS en el frontend?
R: React escapa variables por defecto en JSX. Si hago {data.nombre},
   React lo convierte a string seguro. El riesgo estaría en usar
   dangerouslySetInnerHTML o en no sanitizar URLs de imágenes. Hoy
   no usamos dangerouslySetInnerHTML. La URL de imagen subida se
   almacena como campo y se usa en <img src={...} />, que React maneja
   seguro.

P: ¿Cómo manejarías la expiración de tokens?
R: Agregaría un campo expires_at al modelo AuthToken. En el decorador
   @token_required, verificaría si el token expiró y devolvería 401
   con mensaje "Token expirado". En el frontend, si recibe 401, redirigiría
   al login. También podría implementar refresh tokens con un endpoint
   /api/auth/refresh/.

P: ¿Qué es CORS y por qué lo necesitás?
R: Cross-Origin Resource Sharing. Es un mecanismo del navegador que
   bloquea requests de un origen a otro distinto. Lo necesito porque
   en producción el frontend (Vercel) y el backend (Railway) están en
   dominios diferentes. Sin CORS, el navegador rechazaría los requests.
   En desarrollo lo evitamos con el proxy.

--- Preguntas trampa/conceptuales ---

P: ¿Cuál es la diferencia entre autenticación y autorización?
R: Autenticación es verificar quién sos (login, token). Autorización es
   verificar qué podés hacer (permisos, roles). @token_required autentica,
   pero no autoriza. Los permisos de Django autorizan. En nuestro proyecto
   tenemos autenticación parcial y casi nada de autorización.

P: ¿Qué es N+1 y cómo lo evitás?
R: Es hacer N queries adicionales después de una query principal. Ej:
   traer 100 pedidos y por cada uno hacer una query para obtener el
   mesero. Solución: select_related para FK (hace JOIN) y prefetch_related
   para relaciones inversas (hace 2 queries total). En mis vistas uso
   select_related en algunos endpoints pero no en todos.

P: ¿Cómo harías para que el menú público cargue más rápido?
R: 1) Cache con Redis (TTL de 5 minutos). 2) Paginación. 3) Devolver
   solo los campos necesarios para el menú (nombre, precio, categoria,
   imagen), no todo el objeto plato. 4) Imágenes optimizadas (WebP,
   lazy loading). 5) Si es crítico, SSR con Next.js.

P: ¿Por qué Django no tiene un endpoint /api/status/ o health check?
R: No lo implementé. En producción es esencial para que el load balancer
   verifique que el servidor está vivo. Lo agregaría como un endpoint
   simple que devuelva {"status": "ok"} y opcionalmente verifique la
   conexión a BD y el storage.

P: ¿Cómo harías para que dos cocineros no vean el mismo pedido como
   "pendiente" al mismo tiempo?
R: Con select_for_update() dentro de una transacción atómica. Cuando
   un cocinero toma un pedido, la fila se bloquea hasta que termine la
   transacción. También se podría agregar un campo "asignado_a" en
   Pedido para marcar quién lo está procesando.

P: ¿Cómo integrarías WebSockets para notificar nuevos pedidos en cocina?
R: Usaría Django Channels. Cuando se confirma un pedido, el backend
   envía un mensaje por WebSocket al grupo "cocina". El frontend en la
   página de pedidos se suscribe al grupo y muestra una notificación o
   actualiza la lista sin recargar. Alternativa más simple: polling cada
   5 segundos con setInterval.

--- React específicas ---

P: ¿Por qué usás className y no class en React?
R: class es palabra reservada en JavaScript. React usa JSX, que es
   JavaScript, así que usa className en vez de class para evitar
   conflictos. Al final del día, className se traduce a class en el
   DOM real.

P: ¿Qué es el Virtual DOM y por qué React lo usa?
R: Es una representación en memoria del DOM real. Cuando cambia el
   estado, React calcula la diferencia (diff) entre el Virtual DOM
   actual y el nuevo, y aplica solo los cambios necesarios al DOM real.
   Esto es más eficiente que manipular el DOM directamente.

P: ¿Qué es un hook? ¿Cuáles usaste?
R: Un hook es una función que permite usar estado y ciclos de vida en
   componentes funcionales. Usé useState (estado local), useEffect
   (efectos secundarios como llamadas API), useContext (AuthContext),
   y useNavigate (redirección programática).

P: ¿Qué es el Context API y por qué lo usaste para auth?
R: Context permite compartir datos entre componentes sin pasarlos por
   props manualmente (prop drilling). Lo usé para auth porque casi todos
   los componentes necesitan saber si el usuario está logueado y sus
   datos. AuthProvider envuelve toda la app y expone user, empleado,
   token, login y logout.

P: ¿Por qué no usaste Redux?
R: Para el tamaño del proyecto, Context + useState es suficiente. Redux
   agrega mucha ceremonia (actions, reducers, store) que no justificaba.
   Si la app creciera con más estados globales (carrito de compras,
   notificaciones, configuraciones), evaluaría Zustand o Redux Toolkit.

P: ¿Cómo manejás las rutas protegidas en React?
R: Con un componente AdminRoute que envuelve las rutas de /admin/*.
   Lee token y auth_data de localStorage. Si no hay token, redirige a
   /login con <Navigate>. Si hay token pero no es admin, redirige a /.
   No es 100% seguro porque depende de localStorage, que se puede
   manipular. La seguridad real está en el backend.

--- Arquitectura ---

P: ¿Por qué pusiste todo en un solo archivo views.py?
R: Empezó chico y creció. No lo refactorice a tiempo. Lo correcto sería
   separar en módulos: views/auth.py, views/productos.py, views/pedidos.py,
   etc. Es deuda técnica que habría que pagar antes de que el archivo
   siga creciendo.

P: ¿Cuál es la diferencia entre FK y OneToOne?
R: FK permite muchos registros apuntando al mismo registro (ej: muchos
   empleados pueden tener el mismo Rol). OneToOne es una FK con unique,
   permite solo un registro del otro lado (ej: un User tiene un solo
   Empleado y viceversa).

P: ¿Cuándo usarías GenericForeignKey en lugar de FK?
R: Cuando una FK puede apuntar a diferentes modelos. Por ejemplo, si
   tuviera un modelo Movimiento que puede referenciar un Pedido o una
   Produccion. En este proyecto no lo necesito porque cada relación está
   bien definida.

P: ¿Por qué no usaste signals de Django?
R: No hubo necesidad. La lógica de negocio está en las vistas. Signals
   son útiles para efectos secundarios que deben ocurrir siempre que se
   guarda un modelo (ej: enviar email al crear empleado). Hoy el email
   se envía desde la vista, no con un signal. No está mal, pero signals
   asegurarían que siempre se ejecute incluso si se crea un empleado
   desde el admin de Django.

--- Preguntas de diseño ---

P: Si un cliente quiere saber cuántos platos se vendieron ayer, ¿cómo
   lo implementarías?
R: Crearía un endpoint GET /api/reportes/ventas-diarias/?fecha=YYYY-MM-DD.
   La vista haría una consulta agregada:
   DetallePedido.objects.filter(
       pedido__fecha_creacion__date=fecha,
       pedido__estado='pagado'
   ).values('plato__nombre').annotate(total=Sum('cantidad'))
   Devolvería [{plato: "Milanesa", total: 15}, ...].

P: Cómo modelarías descuentos o promociones?
R: Crearía modelo Promocion con tipo (porcentaje/monto_fijo), valor,
   fecha_inicio, fecha_fin, activo. Y una FK opcional a Plato o
   CategoriaPlato (si la promoción aplica a un plato específico o a
   toda una categoría). Al calcular el total del pedido, verificaría
   si hay promociones activas que apliquen.

P: Cómo manejarías el caso de "plato del día" que cambia cada día?
R: Dos opciones: 1) Modelo PlatoDelDia con FK a Plato y fecha (unique
   por fecha). El menú público filtraría platos del día por fecha actual.
   2) Un campo booleano es_del_dia en Plato que se activa/desactiva
   manualmente cada día. La opción 1 es mejor porque guarda histórico.

--- Preguntas de troubleshooting ---

P: Llegás al trabajo y la API devuelve 500 en todos los endpoints,
   ¿qué hacés?
R: 1) Revisar logs del servidor (heroku logs, journalctl, etc.). 2) Verificar
   que la BD esté corriendo. 3) Revisar si hay errores de sintaxis en el
   último deploy. 4) Verificar variables de entorno. 5) Si nada funciona,
   hacer rollback al último commit estable.

P: Un usuario reporta que puede ver datos de otro restaurante (cuando
   implementen multi-tenant), ¿qué revisás primero?
R: 1) Revisar el middleware de subdominio. 2) Verificar que todos los
   querys filtren por restaurant_id. 3) Buscar querys que no tengan el
   filtro. 4) Revisar que las FK tengan el restaurant_id correctamente.
   La causa más común es olvidar el filter() en alguna vista.

P: El menú público carga bien pero el admin anda lento, ¿por dónde
   empezás a debuggear?
R: 1) Verificar cuántos requests hace el admin al cargar (Network tab).
   2) Las páginas admin hacen muchas llamadas API (empleados + roles +
   turnos, etc.). 3) Ver si hay N+1 en las consultas. 4) Ver si el
   frontend está renderizando muchos componentes sin key o con estados
   que causan re-renders. 5) Perfilar con React Dev Tools.
